### 3. frpc 隧道修复（关键）

- 链路：`api.zeroicey.me (hpazure) → Caddy:443 → 127.0.0.1:18081 → frps → frpc → hpcore:3000`。

### 4. Caddy `keepalive off`（新发现的坑）
- 现象：隧道口（hpazure:18081）稳定 0.18s，但经 Caddy 后偶发 3–18s 慢；DELETE 幂等重试更明显。
- 根因：Caddy 上游 keepalive 默认 2m，超过上游（Bun API）keep-alive 超时 → 连接被重置 → Go transport 对幂等请求重试造成偶发长延迟。
- 修法：`/etc/caddy/Caddyfile` reverse_proxy http transport 加 `keepalive off`（每次请求新建隧道连接，实测 0.18–0.2s），`caddy validate` 通过后 `systemctl reload caddy`。旧文件已备份为 `Caddyfile.bak.*`。

- **网络路径**：本机（中国网络）直连 Azure 公网 IP `104.208.114.194` 不稳定（2–12s、ICMP 全丢），经本机代理 7897 则 ~0.8s。服务器侧无问题。这是**基础设施线路问题**（与旧项目同 IP 同现状），非部署缺陷。若公网客户端体验差，考虑在 api.zeroicey.me 前加 CDN/Cloudflare，或换对华线路更好的云主机。

- **psql 引号坑**：经 `ssh bash -c "..."` 多层嵌套时，SQL 字符串字面量别用双引号（PG 当标识符）。用 heredoc 经 stdin 传 SQL 最稳。
- **本机推 GitHub 要代理**：`https_proxy=http://127.0.0.1:7897 git push …`（直连 receive-pack 超时）。
- **Caddy 改配置**：改前 `sudo cp /etc/caddy/Caddyfile /etc/caddy/Caddyfile.bak.*`，`sudo caddy validate --config …` 后 `sudo systemctl reload caddy`。
- **发布流程**：改代码 → 推 main（docker 出 main）→ `git tag -a vX.Y.Z` 推 tag（docker 出版本+latest，CLI 出 Release）。
